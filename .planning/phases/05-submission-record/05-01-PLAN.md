Face Dataset repo: a pure builder that projects the shared `QcSummary`, an id and repo path minted

D-02, D-03, D-04 and D-14 specify.

every later plan expands outward from the one path this plan proves end to end.

`huggingface_hub`, the fire site in `app.py`'s fresh-run branch, and three test files.
</objective>

    **`qc/submission_record.py`** (new, pure) — module docstring in `qc/mail_config.py`'s framing:
    it states outright that this module imports no UI framework, no `huggingface_hub`, and reads
    no environment or secrets; it takes only a `QcSummary`, the officer dict from
    `auth.current_officer()`, and a file-identity dict, and hands back a plain dict. It records
    the rejected alternatives inline the way `qc/columns.py` does: the full per-check list and a
    bare verdict-and-score record were both offered and not chosen (D-02), so a later contributor
    must not "improve" the record by expanding or shrinking it without a `record_schema` bump.
    Imports are `json`-free, `uuid` and `datetime` only.

    `RECORD_SCHEMA = 1`.

    `mint_record_id_and_path(ts=None)` — when `ts` is `None` use `datetime.now(timezone.utc)`;
    otherwise use the injected value, which is what makes the path partition testable. Build the
    stem as the compact `%Y%m%dT%H%M%SZ` rendering of `ts` joined by an underscore to
    `uuid.uuid4().hex`, and the path as `records/` plus `ts.strftime("%Y")` plus `ts.strftime("%m")`
    plus the stem plus `.json`. Return `(stem, path, ts)` — the three-tuple is deliberate: the
    caller must pass the *same* `ts` into `build_record`, so a record's own `timestamp_utc` can
    never disagree with the month folder it sits in (a record minted in the last second of a
    month is the case that would otherwise split). Docstring states D-14's rejected layouts: a
    flat folder, per-state folders, UUID-only names and sha256-led names were offered and not
    chosen.

    `build_record(summary, officer, file_identity, record_id, ts, version=VERSION)` returns a
    dict with exactly these keys, in this order:
    `record_schema`, `app_version`, `record_id`, `timestamp_utc`, `officer_email`, `file`,
    `verdict_text`, `weighted_score`, `achievable_max`, `layers`.
    `timestamp_utc` is `ts.isoformat()`. `officer_email` is `officer["email"]` when `officer` is a
    mapping carrying a non-empty `email`, else `None` — read no other key off the officer dict,
    because D-01 chose the email alone and names drift. `verdict_text`, `weighted_score` and
    `achievable_max` are the summary's own attributes, assigned straight across with no
    formatting, no rounding and no re-derivation; in particular do not substitute
    `summary.score_display`, which is a presentation string. `layers` is built by iterating
    `qc.report.LAYER_ORDER` and reading `summary.layers[name]`, never by naming layers one at a
    time — that is the shape that left Settlement out of the email in Phase 3 — and each entry is
    `{"checks_run": len(layer.checks), "checks_failing": layer.n_fail, "distinct_issue_rows":
    layer.distinct_issue_rows if layer.source_row_count is not None else None}`. Use
    `source_row_count is not None` rather than `layer.ran`, matching D-02's literal wording: the
    Schema layer's `source_row_count` is always `None`, so Schema's distinct-row figure is null
    whether or not it ran, while a layer that did not run still reports zero checks run.

    `file` is composed inside `build_record` from `file_identity` plus the summary, so the row
    counts are the summary's and not a second count: `{"filename": file_identity["filename"],
    "sha256": file_identity["sha256"], "mlos_rows": summary.layers["MLoS"].source_row_count,
    "takeoff_rows": summary.layers["Takeoffpoint"].source_row_count, "takeoffpoint_file": None or
    {"filename": ..., "sha256": ...}}`. The nested `takeoffpoint_file` is `None` unless
    `file_identity` carries both a `tp_filename` and a `tp_sha256`.

    The function must hold no module-level mutable state and must not mutate `file_identity`,
    `officer` or `summary` — two QC runs building records concurrently share nothing.

    **`submission_log.py`** (new, repo root, sibling of `auth.py`) — module docstring in `auth.py`'s
    "thin wiring only" framing: this module owns nothing but the network-facing wiring; record
    building and id minting live in `qc/submission_record.py`. State that it is the only module in
    the repository permitted to import `huggingface_hub`, and that the worker function must reach
    neither the UI framework nor `auth`, because a fire-and-forget thread outliving the script run
    is exactly the case Streamlit's own documentation says is unsupported for threads calling its
    APIs.

    Module-level: `LOG_TOKEN_VAR = "MLOS_LOG_TOKEN"`, `LOG_REPO_VAR = "MLOS_LOG_REPO"`, a
    `_STATUS` dict, a `_STATUS_LOCK = threading.Lock()`, and `STATUS_CAP = 500`. Import `HfApi`
    from `huggingface_hub` at module scope and reference it through the module global, so a test
    can replace `submission_log.HfApi` with a double.

    `_set_status(record_id, value)` takes the lock, writes, and when the holder exceeds
    `STATUS_CAP` drops the oldest half by insertion order — the app process is long-lived and an
    unbounded holder is a slow leak.

    `get_status(record_id)` takes the lock and returns the stored value, defaulting to `"pending"`
    for an id it has never seen. The four values this module ever stores are `"pending"`,
    `"recorded"`, `"failed"` and `"unconfigured"`.

    `unconfigured_reason()` reads both secrets through `auth.secret(LOG_TOKEN_VAR)` and
    `auth.secret(LOG_REPO_VAR)` and returns `None` when both are non-empty after stripping, else
    one sentence naming the missing variable name or names and stating that QC still runs and
    nothing is recorded. This string is what the officer sees in 05-03; it must name the
    variables, because a feature that silently does nothing is the failure D-10 exists to
    prevent.

    `fire_upload(record, path_in_repo, record_id)` runs on the main script thread. It calls
    `unconfigured_reason()`; when that is not `None` it sets the status to `"unconfigured"` and
    returns `None` without touching the network. Otherwise it resolves `token` and `repo_id`
    through `auth.secret` **here, on the calling thread**, sets the status to `"pending"`,
    constructs `threading.Thread(target=_upload_with_bounded_retry, args=(...), daemon=True)`,
    starts it and returns the thread object. Returning the thread is a testability affordance
    only — no caller in `app.py` may join it, and the docstring says so.

    `_upload_with_bounded_retry(record, path_in_repo, record_id, token, repo_id)` is the worker.
    It serialises the record with `json.dumps(...).encode("utf-8")`, calls
    `HfApi(token=token).upload_file(path_or_fileobj=payload, path_in_repo=path_in_repo,
    repo_id=repo_id, repo_type="dataset", commit_message=...)`, and on success sets the status to
    `"recorded"`. In this task the failure branch may be a single attempt that sets `"failed"`;
    05-02 expands it into D-07's bounded retry schedule. Two constraints are not deferrable and
    must hold from this task on: the token is always passed explicitly to `HfApi`, never left to
