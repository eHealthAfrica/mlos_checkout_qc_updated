<objective>
Remove the organisational addresses from the repository's history, once, behind a gate a human
must actually walk through. Plan 04-02 removed them from the working tree; every commit made
before that fix still carries them, in every clone and every fork, and only a history rewrite
reaches that state.

Purpose: DEPLOY-03. ROADMAP and CONTEXT both insist this stays scoped apart from DEPLOY-02, and
D-08 rates it one-way: a rewrite plus force-push invalidates every existing clone and cannot be
undone once collaborators have re-cloned.

Output: a derived replacement list, a completed rewrite, and an all-refs verification that the
addresses are gone.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 1: Decide whether the rewrite also covers commit authorship metadata</name>
  <decision>Does the one-time history rewrite replace addresses in commit content only, or in commit author and committer metadata as well?</decision>
  <context>
    D-08 already settled the tool and the timing — the rewrite runs once, after the working branch
    has merged to the main line — so this checkpoint does not re-ask a decision you have made.
    One sub-question is genuinely open and is recorded nowhere: DEPLOY-03 names the addresses
    committed in the application source, and a content-only rewrite leaves commit author and
    committer fields untouched. Those fields carry the identity of whoever made each commit,
    which for this repository means a developer address on the same organisational domain.

    This must be answered before the rewrite runs, because both options are the same one-way
    operation. Redoing it after the force-push means a second rewrite, a second round of stranded
    clones, and a second re-clone for every collaborator — the cost D-08 chose the post-merge
    timing specifically to pay only once.
  </context>
  <options>
    <option id="content-only">
      <name>Rewrite commit content only</name>
      <pros>Matches DEPLOY-03's stated subject exactly; preserves the attribution history of every
      commit, which is the record of who did what and is relied on by blame and review; smaller
      and faster operation with fewer ways to go wrong.</pros>
      <cons>A developer address on the organisational domain remains readable in commit metadata,
      so "no organisational address anywhere in the repository" is true of file content but not of
      the commit objects themselves.</cons>
    </option>
    <option id="content-and-authorship">
      <name>Rewrite commit content and author/committer metadata</name>
      <pros>No address on the organisational domain survives anywhere in the object store, content
      or metadata; the strongest reading of the requirement.</pros>
      <cons>Destroys authorship attribution, or replaces it with a placeholder identity, for every
      commit in the project's history; no requirement asks for this; blame output and any external
      reference to a commit author become misleading rather than merely redacted.</cons>
    </option>
  </options>
  <resume-signal>Select: content-only, or content-and-authorship</resume-signal>
</task>

<task type="checkpoint:human-action" gate="blocking-human">
  <name>Task 3: Run the one-time history rewrite and force-push</name>
  <action>Run the one-time history rewrite and force-push, following the D-08 checklist</action>
  <instructions>
    This is the one-way door. A history rewrite plus force-push changes every commit hash from the
    first affected commit onward; once collaborators have re-cloned, it cannot be undone. D-08
    recorded the choice of tool and the timing — after the working branch has merged to the main
    line, so history is rewritten once rather than twice — and that choice is already made. What
    the gate buys is the checklist, not the decision.

    Everything automatable is done: the address set is derived from your actual history, the
    replacement-expressions file is written outside the repository, and the exact command
    sequence is printed above with real paths substituted. Work through these six in order.

    1. **Confirm the merge.** The working branch has merged to the main line. Do not run this
       before the merge; rewriting both separately is the disruption D-08 chose to avoid.
    2. **Notify every collaborator, and confirm nobody has unpushed local work.** Anything not
       pushed at this moment is stranded: after the rewrite their clone's history and the
       remote's have no common ancestor, so it cannot be merged back. This is the step people
       skip and the one that actually loses work.
    3. **Run the replacement on a fresh clone** using the derived file, exactly as printed. The
       tool refuses by default to run on a repository with a configured remote; clone fresh
       rather than defeating that check.
    4. **Verify before pushing.** Run the verifier inside the fresh clone. It must report zero.
       A rewrite that is force-pushed before verification is a rewrite you may have to do twice.
    5. **Force-push all branches and all tags.** Both. A tag left pointing into the old history
       keeps the addresses reachable and the requirement unmet.
    6. **Every collaborator deletes their clone and re-clones.** Existing clones are permanently
       incompatible with the rewritten history; a stale clone that later pushes would restore the
       old objects.

    Apply the authorship scope you selected at this plan's first checkpoint. Under
    `content-only` the command sequence replaces address strings in commit *content* and leaves
    author and committer metadata intact; under `content-and-authorship` it additionally rewrites
    those fields. Use the sequence that was printed for your selection and do not mix the two —
    running the wrong one means a second rewrite and a second round of re-clones.

    Forks and clones already taken by anyone outside your organisation are outside the reach of
    any rewrite. If the repository has ever been public or forked, treat the addresses as
    disclosed and the rewrite as limiting further spread rather than undoing it.
  </instructions>
  <verification>
