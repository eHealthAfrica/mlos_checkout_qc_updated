<planner_clarification>
D-10 says the colliding group is left un-normalised, and then illustrates the consequence: "Rules
needing that column skip exactly as they do for a missing one, and S1 reports it missing."

That illustration holds when neither member of the colliding group is already spelled exactly as the
canonical name — for example `Ward-Code` and `Ward Code`, which both normalise to `ward_code` while
neither is literally `ward_code`. Left un-normalised, the canonical name is genuinely absent, so the
rules skip and `S1` reports it missing, exactly as the illustration says.

There is a second sub-case D-10's sentence does not describe: one member of the group is already
spelled exactly as the canonical name, for instance `Ward Code` alongside a literal `ward_code`.
Leaving both un-normalised keeps that canonical column present and resolvable, so the rules run
against it and `S1` reports it present. `S3` still fails and names both headers, so the officer is
told the header set is ambiguous.

Implement D-10's mechanism literally — detect on the proposed mapping, leave the colliding group
un-normalised, rename everything else — and accept both sub-cases. Do not rename an
already-canonical header away from its canonical spelling in order to force `S1` to report it
missing; that would discard a resolvable column to satisfy an illustrative sentence, against Core
Value. Record which sub-case a test exercises in that test's docstring so the distinction survives.
</planner_clarification>

Expected behaviour, written before the implementation.

`normalize_name`, on single header strings:
- a header with surrounding spaces loses them
- an upper or mixed case header becomes lower case
- a header containing a single space, several consecutive spaces, a tab, a single hyphen or a run of
  mixed spaces and hyphens becomes a single underscore at that position
- a header already containing repeated underscores collapses them to one
- a header that is already canonical snake_case is returned unchanged, so the transform is
  idempotent: applying it twice equals applying it once
- the empty string and a whitespace-only string return the empty string, and no exception is raised

`normalize_columns`, on frames:
- a frame whose headers are all already canonical returns an equal frame, an empty rename map and no
  collision groups
- a frame with the two headers `Ward Code` and `SET_POPULATION` returns a frame whose columns are
  `ward_code` and `set_population`, a rename map with exactly those two entries, and no collisions
- a frame with a header no rule reads, such as `Field Notes`, still renames it to `field_notes` —
  D-09 has no canonical-set membership test
- a frame with the two headers `Ward-Code` and `Ward Code` returns both collision members and leaves
  both headers exactly as they arrived; the returned frame has no duplicate labels, and selecting
  either original header still yields a Series rather than a DataFrame
- a frame with three headers colliding on one normalised name reports one group naming all three,
  not two pairwise groups
- an empty frame with no columns returns an empty rename map and no collisions
- a single-column frame can never report a collision
- the returned rename map contains only headers that actually changed, so a clean submission yields
  an empty map

The non-negotiable ordering assertion: after `normalize_columns` returns for the colliding case,
`len(set(frame.columns)) == len(frame.columns)`. A test that only checks the collision list would
pass against an implementation that renamed first and detected afterwards, which is the defect.
  </behavior>

**`qc/columns.py`.** New module, pure and Streamlit-free. Import shape mirrors `qc/schema.py`:
`pandas` plus relative sibling imports only, never through the package `__init__` — Pitfall 5,
because `qc/__init__.py` imports every layer module and importing back through it produces
partially-initialised-module errors sensitive to import order. Define two module-level compiled
regular expressions as UPPERCASE-style module constants following the repository's convention: one
matching a run of one or more whitespace or hyphen characters, one matching a run of two or more
underscores.

Define `normalize_name(col)`: strip, lower-case, substitute the whitespace-or-hyphen run pattern
with a single underscore, then collapse repeated underscores. Return the result. This is the whole
transform. It performs no canonical-set lookup and no aliasing, per D-08 and the rejected
known-alias deferred idea.

Define `normalize_columns(df, original_names=None)` returning three values: the renamed frame, a
mapping from original header to new header covering only headers that actually changed, and a list
of collision groups. Build it in this order and no other. First, walk the original header list once,
computing each header's normalised form and recording the first header seen for each normalised
form in a dictionary. When a later header normalises to a form already seen, record the collision
and mark every member of that group as collided. Group by normalised form so three headers colliding
on one name produce one group naming all three, not two pairwise groups. Second, build the rename
map from only the headers not marked as collided. Third, apply that map with `DataFrame.rename`.
Fourth, derive the changed-only rename map. Return all three. The function never raises; a collision
is returned as data, matching the codebase-wide convention that a failure is reported as a check
record rather than an exception. Docstring states the ordering requirement and why, citing D-10 and
the empirically verified fact that `rename` does not raise on a colliding target.

Each collision group should carry enough to name the problem in a check description: the normalised
form both headers wanted, and the original headers in the order they appeared in the frame. Choose a
small stable shape and document it, because `qc/schema.py` reads it in task 2.
