performance detail, given the Core Value.

  status lines and per-layer pass counts, and collapsing them would delete that progress reporting.
  D-15 re-affirms the decision, and it was explicitly offered as the stronger structural alternative
  and not chosen. Do not add it as an improvement.
- `getvalue()` on an uploaded file returns the full byte content without moving the read position.
  Verified this session against both a plain `io.BytesIO` and Streamlit's own `UploadedFile`, which
  is itself an `io.BytesIO` subclass and documents this behaviour in its own docstring. So the hash
  can be computed before any `seek` or `read` the loaders perform, and there is no ordering hazard
  and no need for seek choreography.
- Memory note, and the reason this plan asks for one helper called once per file per rerun:
  `getvalue()` returns a new bytes object holding the whole payload. Calling it at each of the three
  key sites would create three transient full-payload copies per rerun. One call per file per rerun,
  with the digest held in a local and reused, keeps the transient cost to a single copy. This matters
  on a free-tier Space where SQ4 is already quadratic and the report builder is memory-hungry.
- Copy-on-Write is unconditional in pandas 3.0 and later, so `mlos_raw` and `mlos_corrected` share
  every unmodified column and only the corrected columns are copied. Holding both does not double
  peak memory for the frame. `02-CONTEXT.md`'s D-14 memory note is pessimistic; do not plan
  mitigation work for it.
- Do not add `@st.cache_data` as an alternative to the manual sha256-keyed session-state pattern.
  They are two independent caching layers, and layering Streamlit's own argument-hashing semantics
  on top of an already-correct manual key adds documented edge cases for file-like objects for no
  benefit. `load_boundary_refs`'s existing zero-argument `@st.cache_data` is a different,
  pre-existing use and is unaffected.
- Do not touch `qc/autocorrect.py`. Its five corrections are correct as written and the identifier
  caching is a session-lifecycle concern that belongs on the Streamlit side of the seam. The module
  docstring already names both defects as this phase's work; this plan closes them from `app.py`.

<planner_clarification>
D-15 says the guard must assert "that `mlos_raw` appears at exactly one call site — the report's
as-submitted sheet."

Read literally against the code, `mlos_raw` is an argument to two calls: `auto_correct_mlos`, which
is the sole producer of `mlos_corrected`, and `build_excel_report`, which writes the as-submitted
sheet. The producer is not a consumer of the raw frame for display or for checking, which is the
class D-15's sentence is about.

The guard is therefore written as: the set of called-function names that receive `mlos_raw` as an
argument is exactly the two names `auto_correct_mlos` and `build_excel_report`, and no other. That
is precise, checkable, and asserts exactly what D-15 protects — that no QC layer, no on-screen
table and no download reads the uncorrected frame. Record this reading in the guard's module
docstring so a future reader does not "fix" the guard toward the literal sentence and break it.

Scope of the no-bare-name rule: the guard applies to module-scope statements in `app.py`, the
orchestration body. Parameter and local names inside `def` bodies are out of its scope, because they
are function-local and unrelated to the session snapshot. To remove the last confusable name at a
call boundary, `build_excel_report`'s MLoS parameter is renamed to make the as-submitted intent
legible in its own signature. `make_longitudinal_df` and `build_longitudinal_mlos` keep their
parameter names; they are pure helpers and the guard asserts what is passed to them, which is what
matters.
</planner_clarification>
